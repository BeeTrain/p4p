# Производительность маскирования

Маскирование использует Python regex с прежними правилами совпадений, объединения пересекающихся диапазонов и исключения диагностики. Демаскирование HTTP JSON, HTTP SSE и WebSocket выполняется в Node.js.

## Процессы и состояние

Каждый HTTP- и WebSocket-обработчик владеет ленивым пулом максимум из двух Python-процессов. Самостоятельные вызовы API и предпросмотр используют отдельный ленивый пул. Один процесс выполняет одну операцию за раз. Контекст сессии направляется в один процесс, а операции одного контекста сохраняют последовательность.

Процесс повторно использует до 16 скомпилированных наборов настроек. Поиск совпадений и диагностики кешируется по контексту, тексту, настройкам и признаку результата инструмента. Кеш хранит исходные диапазоны, а не готовые замаскированные строки. Исключение известных маркеров и применение таблицы замен выполняются при каждом запросе, включая попадания в кеш. Счётчики совпадений и фрагментов также вычисляются для каждого запроса.

На процесс предусмотрено до 4096 записей кеша с бюджетом 16 МиБ, учитывающим размеры текста, ключей, диапазонов и фрагментов. Служебные структуры интерпретатора и активный запрос потребляют дополнительную память. Большие записи не кешируются; вытеснение приводит к повторному поиску с тем же результатом. При удалении или истечении контекста его кеш освобождается. После 30 секунд простоя процесс завершается. Пустой пул не удерживает CLI от завершения; выгрузка обработчика завершает принадлежащие ему процессы и отклоняет незавершённые операции.

Таблицами замен продолжает управлять Node.js. Результат операции принимается после проверки лимитов; ошибка не меняет предыдущую таблицу. Начатые HTTP-ответы используют собственный снимок таблицы. Уничтожение процесса теряет только кеш и не меняет известные маркеры сессии.

## Ограничения

- Выполняющаяся операция ограничена 5 секундами. При превышении процесс принудительно завершается, запрос получает ошибку. Последующая работа запускается в новом процессе.
- Пул допускает до 128 ожидающих операций и до 32 МиБ ожидающих сериализованных данных. Ожидание очереди ограничено 30 секундами.
- Сообщение протокола Node/Python и результат ограничены 64 МиБ.
- Прежние ограничения HTTP/WebSocket на размеры тел и таблиц замен сохраняются.
- Ошибки обработки не включают автоматическую отправку исходного текста.

## Потоковое восстановление

SSE-декодер распознаёт разделители событий и UTF-8 на произвольных границах сетевых порций. Незавершённые маркеры накапливаются отдельно для каналов текста, инструментов и потоков. Полные события передаются по мере готовности. Отмена и ошибки чтения отменяют исходный поток.

При восстановлении меняются только строковые токены JSON. Числа, включая значения вне точного диапазона JavaScript, сохраняют исходную запись. События без замен передаются без изменения байтов. Комментарии и поля `event`, `id`, `retry` сохраняются. Буфер входа и буфер ожидающих восстановленных событий ограничены 16 МиБ каждый. Расширившиеся события передаются отдельными порциями с учётом скорости чтения потребителя. Слишком большой результат восстановления JSON отклоняется до сборки строки.

Схемы инструментов обрабатываются с учётом контекста: свойства с именами `format`, `id`, `type` и другими именами протокольных полей восстанавливаются рекурсивно. Сами протокольные идентификаторы остаются неизменными.

## Локальный бенчмарк

После сборки:

```sh
npm run build
npm run test:performance
npm run test:performance -- --file /path/model-request.json --config /path/p4p.json --runs 30
npm run test:performance -- --file /path/model-request.json --probe-pattern '\bconst\b'
```

Без файла используется искусственная история из 218 сообщений и словарь из 14 правил. С файлом обрабатывается поле `request` или переданный JSON целиком; по умолчанию читается стандартная конфигурация p4p. `--config` выбирает другую конфигурацию. Маскирование принудительно включается только в памяти бенчмарка. `--probe-pattern` добавляет тестовый regex только в памяти. Настройки и входной файл не изменяются, внешние модели не вызываются.

Вывод содержит размеры, количество правил и замен, медиану, p95 и число запусков процесса. Тела запросов и таблицы замен не выводятся. Метрики памяти относятся к Node.js, а не ко всем Python-процессам.

Сравниваются:

- Одноразовый Python-процесс и работающий процесс без кеша строк.
- Работающий процесс с прогретым кешем, HTTP-обработчик с прогретым кешем и растущая история.
- Восстановление искусственного JSON-ответа около 25 КБ и SSE с маркерами, разбитыми между событиями.

Первый запуск пула измеряется отдельно. Перед замерами проверяется совпадение результатов, таблиц и статистики с одноразовым движком и восстановление исходного запроса. Для сравнения с сохранённой предыдущей версией Python можно указать `--reference-engine /path/engine.py`; рядом должен находиться её `diagnostic_fragments.py`.

Бенчмарк измеряет локальную обработку. Время сети, генерации модели и записи журнала запросов в HTTP-замер не входит. JSON-замер восстановления получает готовый объект, а SSE-замер — заранее подготовленный поток; эти результаты не являются временем ответа модели.

Для измерения всей последовательности обработчиков, включая чтение настроек, подготовку записей и запись журнала на диск, есть отдельный сценарий:

```sh
mkdir -p test-results
npm run test:performance:full -- --plugin /path/to/p4p --file /path/model-request.json --probe-pattern '\bconst\b' --runs 30 --output test-results/full-path.json
```

`--plugin` выбирает собранную копию плагина, включая глобально установленную. Сценарий сравнивает JSON и SSE, включённый и выключенный журнал, повторную историю и новые контексты. Отдельно измеряются обработчики начала запроса, маскирования, отправки, получения ответа и полного чтения восстановленного ответа. Последовательность вызовов соответствует HTTP-перехватчикам плагина.

Настройки и журналы теста находятся во временной папке и удаляются после замера. Рабочая конфигурация проверяется на отсутствие изменений. Ответ готовится локально; сеть, генерация модели и отрисовка Desktop не входят в результаты. Во всех режимах проверяются количество замен, восстановление ответа и итоговый статус записей журнала. Добавленный тестовый regex не сохраняется в рабочую конфигурацию.

## Проверки корректности

`npm test` включает сравнение кешированного и одноразового движков, комбинации настроек диагностики, изменение таблиц и правил, ограничение кеша, таймаут и перезапуск процесса, завершение очереди, разрывы маркеров и UTF-8, изоляцию каналов, точность чисел SSE, отмену потока и восстановление схем инструментов. `npm run test:live` проверяет интеграцию с установленным OpenCode и локальной тестовой моделью.
