# Повторяемый парный тест кеша p4p

Скрипт сравнивает установленный HTTP-обработчик p4p с прямой отправкой того же исходного сценария. Рабочие конфигурации не изменяются. Перед стартом настройки p4p копируются в отдельную временную папку с закрытым доступом; все пары используют эту неизменную копию. Изменения исходного словаря в Desktop во время измерения не влияют на тест. Используется Chat Completions API; вызовы идут напрямую к настроенному провайдеру, без запуска Desktop.

## Запуск

Из корня репозитория после `npm ci` и `npm run build`:

```sh
npm run test:cache -- --model provider/model --dry-run
npm run test:cache -- --model provider/model --pairs 10 --requests 20
```

Первый запуск выполняет только локальные проверки и маскирование, без запросов к модели. Второй выполняет 400 реальных вызовов с короткими ответами. Модель должна присутствовать в выбранном конфиге OpenCode, её хост должен быть включён в p4p. Ключ берётся из `provider.<id>.options.apiKey`; поддерживаются буквальное значение и `{env:NAME}`. Ключи не выводятся и не записываются в результаты.

Явное указание всех путей:

```sh
node scripts/cache-benchmark.mjs \
  --model provider/model \
  --opencode-config /path/to/opencode.jsonc \
  --p4p-config /path/to/p4p/config.json \
  --plugin /path/to/installed/p4p \
  --scenario scripts/cache-benchmark/scenario.json \
  --pairs 10 \
  --requests 20 \
  --interval-ms 5000 \
  --global-interval-ms 2500 \
  --margin-pp 5 \
  --seed p4p-cache-ab-v1
```

Если `--plugin` отсутствует, используется абсолютный путь из подключения p4p в конфиге OpenCode; иначе — сборка этого репозитория. Путь к настройкам p4p берётся из `--p4p-config`, `plugins[].options.config` либо стандартных настроек движка. Конфиг OpenCode по умолчанию — `$XDG_CONFIG_HOME/opencode/opencode.jsonc` или `~/.config/opencode/opencode.jsonc`. `--model` можно не указывать, если модель по умолчанию подходит для теста. Поддерживаются собственные заголовки `provider.<id>.options.headers`. Произвольные параметры SDK и расширенные настройки моделей не переводятся автоматически в поля API; сценарий отправляет фиксированные параметры Chat Completions.

По умолчанию результаты находятся в `test-results/cache-benchmark/<дата>-<идентификатор>/`. Можно задать `--output DIR`. Для каждой проверки выбирайте новую папку. Каталог `test-results` исключён из Git.

## Сценарий

`scenario.json` содержит синтетические системные инструкции, шаблон справочных записей, схему инструмента, шаблон пользовательского сообщения и фиксированный ответ для истории. В нём нет рабочих данных проекта. Начальный сценарий содержит отдельное слово `auth`, поэтому правило `(?i)\bauth\b` действительно выполняет маскирование.

В отличие от стресс-теста с секретом в каждой строке, здесь совпадения находятся в инструкциях и описании инструмента. Плотность маскирования можно менять через собственный файл `--scenario`. Перед реальным тестом нужно убедиться, что сценарий содержит синтетические совпадения с вашим текущим словарём. Если замен нет, локальная проверка остановит тест.

На каждом шаге добавляются новое пользовательское сообщение и заранее заданный ответ предыдущего шага. Реальный ответ модели не влияет на последующие запросы. Описания инструментов остаются неизменными; `tool_choice: none` запрещает их вызов. Инструменты локально не выполняются.

## План эксперимента

- Каждая пара содержит отдельную сессию с p4p и отдельную сессию без него.
- Начальные уникальные префиксы разных сессий разделяют их кеши. Префиксы одного формата и одинаковой длины. Точное число токенов может отличаться из-за токенизации и маскирования.
- Два рабочих процесса изолируют состояние режимов. В каждом режиме одна таблица замен сохраняется в течение сессии и удаляется после пары.
- На каждом шаге выполняются оба режима. Порядок первой отправки сбалансирован и перемешан с указанным `seed`. Новый запуск создаёт новые префиксы, чтобы не использовать кеш предыдущего теста. `seed` воспроизводит порядок и bootstrap, но не старые префиксы и не случайные маркеры движка.
- Одновременно отправляется один запрос. Соблюдаются минимальные интервалы между началами запросов одной сессии и всех запросов в целом.
- Проверяются неизменность инструкций, схем инструментов, ранее отправленной истории, тестовой копии настроек, конфигурации провайдера OpenCode и файлов движка. Ошибка целостности останавливает прогон. Изменения исходного рабочего файла p4p только отмечаются в плане: тест продолжает использовать исходную копию.
- API-ошибки и отсутствующие метрики не считаются промахами. Автоматических повторов запросов нет. Ошибки 400/401/403/404, успешный ответ без метрик кеша или три последовательные сетевые/API-ошибки останавливают прогон; завершённые попытки сохраняются. Порог последовательных ошибок задаётся через `--max-consecutive-errors`.

## Оценка

Основная метрика — средняя разница частоты попаданий после первого запроса внутри каждой полной пары: `p4p − без p4p`. Первый запрос каждой сессии отдельно учитывается как холодный старт; попадания после него не предполагаются автоматически.

95%-й доверительный интервал вычисляется percentile bootstrap с повторной выборкой целых пар сессий, 20 000 выборок. Запросы одной сессии не рассматриваются как независимые наблюдения. Дополнительно считаются общая частота попаданий, доля кешированных входных токенов, объём входа и время обработки.

Порог практической эквивалентности задаётся до запуска: по умолчанию ±5 процентных пунктов. Вывод об укладывании в порог делается только если весь интервал находится внутри этих границ. Если интервал широкий, результат считается неопределённым. При неполных парах или отсутствии попаданий в одном из режимов вывод об эквивалентности не делается. Начальные 10 пар — пилотная оценка; для узкого интервала могут потребоваться дополнительные независимые пары. Методика и выбранный порог должны оставаться фиксированными при расширении эксперимента.

Отчёт относится к выбранному сценарию, модели, прокси, настройкам и времени измерения. Он не гарантирует аналогичный эффект для других конфигураций. Процентные границы bootstrap приблизительны, особенно при небольшом числе пар и редких попаданиях.

## Результаты

- `plan.json` — параметры, независимые префиксы, порядок отправки, версии и хеши настроек, кода и сценария; путь и ревизия исходного рабочего файла p4p, признак использования копии.
- `preflight.json` — метрики локальной проверки без сети.
- `requests.jsonl` — все реальные попытки, метрики провайдера, хеши запроса и проверки целостности; без ключей, текстов запросов и таблиц замен.
- `analysis.json` — агрегаты, результаты по парам, доверительные интервалы и формальный вывод.
- `REPORT.md` — читаемый отчёт.

Временная копия настроек p4p удаляется после успешного завершения и после локальной проверки без сети. При ошибке во время реального прогона копия сохраняется для продолжения; её путь записан в `plan.json`. Она не содержит ключа провайдера и не включается в отчёт. Системный каталог временных файлов может очищаться ОС: при необходимости сохраните копию в своём закрытом каталоге и передайте её через `--p4p-config`. После удаления временной копии отчёт по JSONL по-прежнему можно пересчитать: для анализа настройки не нужны.

Отчёт обновляется после каждой завершённой пары. После нормального завершения применяется 20 000 bootstrap-выборок. Прерванный запуск сохраняет уже записанные строки; повторный анализ не обращается к модели:

```sh
node scripts/cache-benchmark.mjs --analyze test-results/cache-benchmark/RUN
```

Этот режим можно использовать после остановки или для восстановления отчёта. Он не возобновляет отправку запросов.

## Продолжение после сбоя

После восстановления доступа к провайдеру:

```sh
node scripts/cache-benchmark.mjs --resume test-results/cache-benchmark/RUN --dry-run
node scripts/cache-benchmark.mjs --resume test-results/cache-benchmark/RUN
```

Полные пары сохраняются. Неполные пары целиком повторяются с новыми независимыми префиксами в обоих режимах: частичная сессия не продолжается с новой таблицей замен. Предыдущие попытки и план сохраняются в `attempts/<дата>/`, выбранные полные пары остаются в основном `requests.jsonl`. Все повторения отмечаются в `plan.json`. Участки, пришедшиеся на сетевой сбой, не превращаются в промахи кеша.

Скрипт откажется продолжать при изменении модели, адреса, конфигурации провайдера, хеша настроек, сценария или кода плагина. Копия настроек ищется сначала по сохранённому временному пути, затем в исходном рабочем файле при точном совпадении хеша. Если копия перенесена, укажите `--p4p-config /path/to/matching-settings.json`. Продолжение с `--dry-run` проверяет всё локально, не меняет старый план и не отправляет запросы.

Пауза между полными парами допускается: сравнение остаётся парным внутри каждого временного блока. Длительный перерыв нужно учитывать при интерпретации; сведения о нём сохраняются в журнале возобновлений.

## Промпт для будущего запуска агентом

> Проведи парный A/B-тест влияния p4p на кеш скриптом `scripts/cache-benchmark.mjs` согласно `scripts/cache-benchmark/README.md`. Используй текущий конфиг p4p и модель `PROVIDER/MODEL` из выбранного конфига OpenCode. Сначала выполни `--dry-run`, затем 10 пар сессий по 20 запросов в каждом режиме, интервалы 5000/2500 мс, порог ±5 п.п. Не меняй рабочие настройки. Не публикуй ключи, таблицы замен и тексты запросов. Дождись окончания и проверь все 400 попыток, стабильность инструкций, инструментов и истории. Покажи частоту попаданий с плагином и без, разницу по парам с 95%-м интервалом, долю кешированных токенов и увеличение входа. Различай практическую эквивалентность, обнаруженное отличие и недостаточность данных. Дай ссылки на скрипт и полный отчёт. Если тест остановился, сообщи конкретную причину и сохрани результаты частичного прогона.
